# 08. 9/1 に対する実現可能性の率直な評価

結論を先に書きます。**忖度した全肯定はしません。**

## 8.1 結論

| 対象 | 判定 | 根拠 |
|---|---|---|
| **9/1に公開URLが存在し、ファン1名が選手比較を操作する** | **達成可能（確度 高）** | 中核3機能はseedデータだけで成立する。外部依存がない |
| Phase 0 / 1 / 2（設計・UI全体・管理基盤） | **達成可能（確度 高）** | グリーンフィールドで既存資産との整合作業がない。5週間は妥当 |
| 法務ページ・問い合わせ | **達成可能（確度 高）** | 前倒し提案（`W3-11`）で終盤の混雑から外す |
| **Phase 3（API実データでの公開）** | **五分五分。オーナーの返信待ちが律速** | §8.3 |
| **Phase 4（画像）** | **確度 低。ストレッチのまま扱うべき** | §8.4 |
| 「全機能が完成した状態」での9/1公開 | **不可能** | ただしオーバーライド §1 が「全機能の完成を公開条件にしない」と明記しており、**元々そういう計画になっていない** |

**総評:** この計画は**日付を守る設計として正しく作られています。**
中核（選手名鑑・比較）が外部依存ゼロで成立し、外部依存のあるもの（API・画像）が全部ストレッチ側に置かれている。
9/1に落ちる可能性が高いのは「実データが載っているか」であって「公開できるか」ではありません。

## 8.2 いま最も危ないのは技術ではなく「日程の初期条件」

**オーバーライドは Week 0 を 7/27〜7/29 と定義していますが、本日は 7/28 です。**
Week 0 のオーナータスク7件（約4.5〜5.5時間）が、**実質あと1.5日**しか残っていません。

- 特に `W0-1`（BALLDONTLIE契約条件の書面確認）は**返信待ちが発生する唯一のタスク**で、
  オーバーライド §6 が「回答が **8/10まで**に得られなければ Phase 3 を外す」と定めています。
- 今日か明日に送れば、返信まで約2週間の猶予があり間に合います。**1週間送るのが遅れると、8/10判定は実質「不合格」になります。**
- Supabase / Vercel のアカウント作成（`W0-2`〜`W0-4`、計45分）が遅れると、
  **8/5 チェックポイント（Vercelに空アプリがデプロイ済み）が物理的に達成できません。**
  AIタスク `W1-11` はオーナーのアカウントなしには実行不能です。

**これが現時点で唯一の「即日アクション」です。** 技術的な課題はどれもこれより後ろにあります。

## 8.3 Phase 3（API実データ）が五分五分である理由

3つの独立した関門があり、**すべて通らないと実データ公開になりません。**

| 関門 | 内容 | 通過確度 |
|---|---|---|
| ① 回答が8/10までに返る | 商用APIの規約照会。返信の速さはこちら側で制御できない | 中 |
| ② **自社DBへの永続保存が許諾される** | 許諾されない場合、15テーブル前提の設計がキャッシュ主体に作り直しとなり、**9/1を確実に落とす**（オーバーライド §6） | 不明（最大の未知） |
| ③ 必要なデータが実際に取れる | チーム公式成績 / シーズン途中移籍のstint分割 / プレーオフ / 過去シーズン範囲。**プランによっては取れない** | 中 |

**②が最も重い**ですが、本設計はここに保険をかけています。
`SeedProvider` が正規のプロバイダとして最初から実装されるため、**②が否だった場合の作業は環境変数の切り替えのみ**です（[05_PROVIDER_ADAPTER.md](./05_PROVIDER_ADAPTER.md) §5.6）。
つまり **Phase 3 が落ちても9/1は落ちません。** 落ちるのは「実データが載っているか」だけです。

③については、モックに描かれている **BPM / VORP** が特に危険です。
これらは一般に高度指標として上位プランでのみ提供されるか、提供されないことが多く、
**環境の制約により、本日AI側からBALLDONTLIEの提供範囲を確認できませんでした**（[02_ENVIRONMENT.md](./02_ENVIRONMENT.md) §2.4：ドキュメントサイトが403）。
`ProviderCapabilities.metrics` に含まれない指標は**画面に列自体を出さない**設計にしてあるため、
取れなかった場合も「空欄が並ぶ」ことにはなりませんが、モックとの見た目の差は発生します（→ Q2）。

## 8.4 Phase 4（画像）を「ストレッチ」から昇格させない方が良い理由

1. **オーナー作業が2〜3時間発生し、それが最終週にある。** 最終週は公開判断と被験者連絡が入る、最も動かせない週です。
2. **人物一致の判定はAIが代替できません。** 「AIは自分の出力が事実か判定できない」という前提を、この作業は正面から踏みます。
3. **Wikidata / Wikimedia Commons APIへの到達性が未検証です。** 開発環境から `nba.com` と `docs.balldontlie.io` が403だったことを踏まえると、Commons APIも同様に弾かれる可能性があります。弾かれた場合、Phase 4は環境要因で実行不能になります（Phase 4着手前に到達性確認を行います）。
4. 代替表示（背番号・イニシャル・チームカラー）は**それ自体がA案のデザインと相性が良く**、写真がなくても成立します。

**推奨:** 画像は最初から「9/1後」に置くことも十分合理的です。
ただしオーバーライド §5 は「チェックポイント未達時に削る」と定めているため、**先回りして削ることはしません。**
`W4-11`（8/26判定）の時点で、実データ検証の消化状況を見て一緒に判断することを提案します。

## 8.5 スコープが溢れた場合の提案（削減ラダーに沿って）

現時点で溢れる兆候はまだありませんが、チェックポイント別に**あらかじめ判断基準を固定**しておきます。
遅延が起きてから議論すると、そこで数日失うためです。

| チェックポイント | 未達だった場合の実行内容 |
|---|---|
| **8/5** Phase 0承認・空アプリデプロイ | 未達＝オーナーのアカウント作成待ち。**機能は削らず、Week 1のAIタスクをローカルDBで先行させる**（Docker があるため可能）。デプロイだけ後ろ倒し |
| **8/12** 選手比較がseedで動作 | 削減ラダー **2番（チーム比較）を即実行**。チーム詳細・年代別ロスターは残す |
| **8/19** 管理画面と同期基盤が動作 | 削減ラダー **3番（ランキング）を実行**。`ranking_rules` のスキーマは残すので、公開後に戻せる |
| **8/26** 実データ確定 | 削減ラダー **1番（画像を丸ごと公開後）を実行**し、seed公開へ切替。「データ準備中のサンプル・非公式サイト」を明示して公開する |

**どのシナリオでも `選手比較 / 選手詳細 / 選手一覧` には手を付けません。** ここが中核仮説であり、これを削ったら公開する意味がなくなります。

## 8.6 この計画で私が最も懸念している見落とし

技術リスクではなく**仕様の空白**です。詳細は [11_OPEN_QUESTIONS.md](./11_OPEN_QUESTIONS.md) Q4。

> **選手名の日本語（カタカナ）表記を、どこから持ってくるかが、要件定義書にもオーバーライドにも書かれていません。**

- モック7枚すべてで選手名はカタカナ表示です（「ジェイレン・モリス」等）。
- しかしスタッツAPIは英語名しか返しません。Wikidataの日本語ラベルも、NBA選手全員には付いていません。
- seed 20〜30名なら手入力で済みますが、**API連携が成功して1,200名規模になった瞬間に破綻します。**
  「英語名のまま表示する」「機械的にカタカナ化する（誤変換が残る）」「上位N名だけ手作業」のいずれかを選ぶ必要があります。
- **9/1のseed公開シナリオでは表面化しません**が、Phase 3が成功した場合にだけ牙を剥くタイプの問題です。
  スキーマ側は `players.full_name_ja` + `name_ja_state`（未設定 / 機械 / 人手確認済み）で受けられるようにしてあり、
  どの結論でも作り直しは起きません。**決定はWeek 0でなくWeek 3まで待てます。**

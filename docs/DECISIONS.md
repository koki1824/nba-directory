## W0-6 ［保留］4項目（決定日 2026-07-29 / オーナー承認済み）

### 1. シーズン当時年齢の基準日 = **そのシーズンの開幕日**

- **決定**: 「シーズン当時の年齢」は、**当該シーズンのレギュラーシーズン開幕日**時点の満年齢とする。
- 出典: 要件定義書 4.3「シーズン当時年齢の基準日は未確定。開幕日または固定日をユーザー承認後に採用する。」

**実装への影響（W1-5 / W1-7 で必ず反映すること）**

- `seasons` テーブルに **開幕日カラム（`regular_season_start_date`）を必ず持たせる。** 年齢計算がこの列に依存するため、後付けにしない。
- 開幕日は reference seed（`W1-7`）で全シーズン分を投入する。API から取得できる保証がないため、**seed を正とする**。
- ロックアウト・パンデミック等で開幕が変則だったシーズン（1998-99 / 2011-12 / 2019-20 / 2020-21 など）は、
  実際の開幕日を個別に確認して投入する。ここを推測値で埋めないこと。
- 開幕日が未投入のシーズンでは、**当時年齢を表示しない**（推測で出さない）。
  値としては `N/A` 扱いとする（オーバーライド §8「0 / NULL / N/A / Not calculated を区別する」）。
- 実装は `seasons.opening_date` を `age_reference_date` にコピーして使う（[11_OPEN_QUESTIONS.md](./11_OPEN_QUESTIONS.md) §11.1 Q-a）。

**既知のトレードオフ（オーナー了承済み）**

Basketball Reference など英語圏の主要スタッツサイトは「シーズン終了年の2月1日時点」の年齢を採用しています。
本サイトは開幕日基準なので、**選手によっては他サイトと年齢が1歳ずれて見えます。**
`W2-13`（seed数値の抜き取り確認）や `W4-7`（実データ検証）で他サイトと突き合わせた際、
年齢の差異は不具合ではなく仕様です。混乱を避けるため、**選手詳細ページに「年齢はシーズン開幕日時点」と明記する**こと。

### 2. 選手比較の同時比較人数 = **4人**（実装順は2人レイアウトを優先）

- **決定**: 上限は **4人**。2026-07-28 のオーナー決定（推奨案2人からの変更）を正式仕様として維持する。
- 出典: [11_OPEN_QUESTIONS.md](./11_OPEN_QUESTIONS.md) §11.1 Q-b、§11.6。
- モックの食い違い（トップ「最大5人」／比較「最大3名」／トレー「2/5名」）は**すべて4人に統一**する。

**実装への影響（`W2-7` / `W2-11`）**

- 比較ページは**人数に応じてレイアウトを切り替える**。2人用と4人用を別ページにしない（URLが分裂するため）。

  | 人数 | レイアウト |
  | --- | --- |
  | 2人 | モック `02_compare.jpg` どおりの**対比レイアウト**（左右対置・双方向パーセンタイルバー） |
  | 3〜4人 | **表形式**（選手を列・指標を行）。パーセンタイルは各選手1本の横バー |

- **実装順は2人レイアウトを先に完成させる。** 3〜4人の表形式はその後に足す。
  §11.6 が「8/12チェックポイントで遅延した場合は2人レイアウトを優先し、3〜4人対応を公開後に回す」と定めており、
  最初からその順で作れば、遅延しても縮退の判断だけで済み、作り直しが発生しない。
- URL は `?p=` を最大4つまで受け付け、**5つ以上は無視して先頭4件に丸める**（エラーにしない）。
- モバイルは4人だと横幅が足りないため、指標行を主体にした横スクロール表 + 主要4指標のみ上部固定。
- データ層は人数に依存しない。比較対象は「固定スロット」ではなく**選手IDの配列**として扱い、
  上限は表示層の定数（`MAX_COMPARE_PLAYERS = 4`）で制御する。

### 3. 仮サイト名 slug = **`nba-directory`**

- **決定**: URL・Vercelプロジェクト名・リポジトリ名をすべて `nba-directory` で統一する（オーナー決定 2026-08-02）。
- 出典: 要件定義書「正式サイト名・ドメイン・最終ロゴデータは後日決定」［保留］。

> **⚠️ この項目は [11_OPEN_QUESTIONS.md](./11_OPEN_QUESTIONS.md) §11.1 Q-c を上書きします。**
> 同文書は 2026-07-28 時点で `nba-meikan`（第2候補 `court-archive`）と記録していますが、
> 2026-08-02 のオーナー決定により `nba-directory` に変更されました。
> 11_OPEN_QUESTIONS.md は当時の記録として原文のまま残しています。**決定の正はこのファイルです。**

**実装への影響**

- あくまで**仮**。正式サイト名の決定後に変更しうる。
- 表示名（`<title>` やヘッダー）にこの slug を直接使わないこと。表示名は差し替え可能な1箇所に集約する。
- ロゴ（`W1-4`）は、要件定義書の指示どおり**サイト名が変わってもシンボルを流用できる構造**にする。

### 4. プレーオフのランキング規定 = **全選手表示＋試合数明示**

- **決定**: プレーオフのランキングでは**独自の最低試合数を設けず、全選手を表示**し、**試合数を必ず併記**する。
- 出典: 要件定義書「プレーオフにレギュラーシーズンの58試合規定を流用しない。公式基準がない指標は全選手表示 + 試合数明示とする。」

**実装への影響**

- `ranking_rules`（`W1-5` / `W3-6`）は **RS と PO で別レコード**として持つ。PO 側は最低条件なしを表現できる形にする。
- ランキング画面（`W2-10`）は、PO のとき「最低条件なし・試合数を併記」と画面上に明示する。
- 公式基準が存在する PO 指標が見つかった場合は、この決定を上書きせず**追加の行として記録**してから実装する。
- レギュラーシーズン側の規定（58試合等）と公式例外の扱いは `W3-10` の対象であり、本決定の範囲外。

### 7. 開発の運用方法

**目的はオーナーの操作を最小にすること。** 停止期間中に失われたのは作業時間だけで、成果物は GitHub に push してあったため無傷だった。この経験を踏まえて次のとおり固定する。

| 項目 | 決定 | 理由 |
| --- | --- | --- |
| コードの反映 | **`main` に直接 push**。PR は挟まない | 1人開発でレビュアーがいないため PR は儀式になる。CI が門番を務める |
| デプロイ | **Vercel の GitHub 連携で自動** | push のたびに公開URLが更新される。オーナーの操作はゼロ |
| ファイルの受け渡し | **GitHub に一本化**。デスクトップ経由のアップロードは行わない | AI 側は使い捨てのコンテナで動くため、push したものだけが残る。実際 8/2〜9/5 の停止中にコンテナは作り直されたが、リポジトリの内容は無傷だった |
| オーナーの役割 | **公開URLを見て OK / NG を言う**、それだけ | 判断に専念してもらい、作業は AI 側で完結させる |

### 9. `engines.node` の書き方 — Vercel が解釈できる形にする

> **2026-09-05 訂正:** この変更を「Vercel のデプロイ失敗の原因」として記録していましたが、**誤りでした。**

  **`src/test/setup.ts` の起動時チェックで見張る**。古い Node ではテストが明確なメッセージで即座に止まる。

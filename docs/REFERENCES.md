# REFERENCES — 採用した実装パターンと出典

このファイルは「なぜこの書き方を選んだか」の記録です。同じ領域を次に触るときは**再調査せず、ここに従います**。
判断を変えたいときは、行を書き換えたうえで理由を残してください。

> **この時点での制約（重要）**
> 開発環境からの外部Webアクセスがegressポリシーで遮断されており（nextjs.org / typescriptlang.org / prettier.io すべて HTTP 403）、
> 公式ドキュメントを直接読んで裏取りすることができませんでした。到達できたのは npm レジストリのみです。
> そのため下表のうち **［暫定］** と付けた行は「公式ツールの出力」と「広く定着した慣行」に基づく仮決定です。
> 外部アクセスが通る環境になった時点で公式ドキュメントと突き合わせ、必要なら差し替えてください。

## W1-1 プロジェクト初期化

### 1. プロジェクト雛形の作り方

| 項目 | 内容 |
| --- | --- |
| 対象領域 | Next.js アプリの初期構成（ディレクトリ・設定ファイル） |
| 採用パターン | 公式CLI `create-next-app@15.5.22` の出力を基点にし、そこから差分で調整する |
| 出典 | `npx create-next-app@15.5.22 --ts --tailwind --eslint --app --src-dir --import-alias "@/*"` の生成物（公式ツールの出力そのもの） |
| 採用理由 | 手書きで設定ファイルを組むより、公式が「これが標準」として吐く構成に乗るほうが、バージョン追従時に情報が見つかりやすい。App Router / `src/` / `@/*` エイリアスはいずれも公式CLIの既定選択肢。 |
| 不採用の代替案 | 設定ファイルを一から手書きする案。→ 公式の既定から外れると、エラー時に検索で解決策が出てこなくなるため不採用。 |

### 2. Next.js のバージョン

| 項目 | 内容 |
| --- | --- |
| 採用パターン | `next@15.5.22`（15系の最新安定版）にピン留め |
| 採用理由 | ROADMAP `W1-1` の指定が「Next.js 15」であるため。パッチ更新まで取り込みつつメジャーは動かさない。 |
| 不採用の代替案 | Next.js 16系。→ ROADMAP の指定から外れる。**ただし後述のセキュリティ項目に関係するため、16系への移行は別途オーナー判断が必要**（下の「未解決」参照）。 |

### 3. TypeScript の厳しさ設定 ［暫定］

| 項目 | 内容 |
| --- | --- |
| 採用パターン | `strict: true` に加えて `noUncheckedIndexedAccess` / `noImplicitOverride` / `forceConsistentCasingInFileNames` を追加で有効化 |
| 採用理由 | 本プロジェクトでは型チェックが「オーナーの代わりにコードを読む目」であり、緩めると品質保証の手段が消える。特に `noUncheckedIndexedAccess` は、DBの行や外部APIのレスポンスを配列で受けたときに「その要素、無いかもしれない」を型で強制する。欠損値を0扱いしない（オーバーライド §8）という要件と方向が一致する。 |
| 不採用の代替案 | `exactOptionalPropertyTypes` も有効化する案。→ Supabaseの生成型やReactの型と衝突しやすく、初期段階で開発が止まるリスクが上回るため見送り。W1-8（型生成）の結果を見て再検討する。 |
| 補足 | `target` は公式CLI既定の `ES2017` から `ES2022` へ引き上げ。Node 20以上（`W0-5`）を前提にできるため。 |

### 4. ESLint と Prettier の組み合わせ ［暫定］

| 項目 | 内容 |
| --- | --- |
| 採用パターン | 役割を分ける。**ESLint = コードの正しさ / Prettier = 見た目の整形**。`eslint-config-prettier` を flat config の**最後**に置いて、整形系ルールだけを無効化する。 |
| 採用理由 | 両者に整形ルールを持たせると同じ箇所で反対の指示が出て、保存のたびに差分が揺れる。`eslint-config-prettier` は「ESLint側の整形ルールを黙らせる」だけの設定集なので、衝突が構造的に起きない。 |
| 不採用の代替案 | `eslint-plugin-prettier`（Prettierを1つのESLintルールとして走らせる）。→ 整形の差分が大量のlintエラーとして出て読みにくく、lintも遅くなる。Prettier公式も推奨していない構成として知られているため不採用。 |
| 補足 | `prettier-plugin-tailwindcss` を入れ、Tailwindのクラス順を機械的に統一。クラス順の指摘をレビュー対象から外すため。 |

### 5. Prettier の適用範囲

| 項目 | 内容 |
| --- | --- |
| 採用パターン | `docs/` を `.prettierignore` に入れ、**オーナー提供の文書は整形しない** |
| 採用理由 | 初回に `prettier --write .` を流したところ、`docs/ROADMAP.md` と `docs/開発方針オーバーライド_v3.md` が自動整形され差分が出た。原本の文書はレビューの基準になるため、機械整形で行が動くと差分の追跡が難しくなる。 |

## W1-2 テスト基盤とCI

### 6. Nodeのバージョン指定 ［CIの実失敗から確定］

| 項目 | 内容 |
| --- | --- |
| 対象領域 | 開発環境とCIのNodeバージョン管理 |
| 採用パターン | **`.nvmrc` に一本化**し、CIは `node-version-file: .nvmrc` で読む。`package.json` の `engines` と `.npmrc` の `engine-strict=true` で、条件を満たさないNodeでは `npm install` の時点で止める |
| 採用理由 | CIのNodeを `20` と直接書いていたところ、**単体テストだけがCIで失敗**した（手元はNode 22で成功）。原因は `jsdom@30` が同梱する `undici@8` が `node:worker_threads` の `markAsUncloneable` を使っており、これがNode 22.22.2以降にしか無いこと。エラーは `webidl.util.markAsUncloneable is not a function` という原因の分かりにくい形で出た。バージョンの指定場所が2箇所あったことが根本原因なので、1箇所に統合した。 |
| 不採用の代替案 | ①CIのNodeだけ22に上げる → 指定が2箇所に残るので同じ事故が再発する。②jsdomをhappy-domに置き換えてundiciを避ける → 症状は消えるがNodeのバージョン差という本当の原因が残り、他の依存で再発する。 |
| 影響 | ROADMAP `W0-5` の「Node.js 20以上」を **22.22.2以上**へ引き上げた。 |

**この失敗自体がCIの価値の実例です。** 手元では4種類の検査が全て緑でしたが、CIがNodeの差を捕まえました。

## W1-3 デザイントークンとUIプリミティブ

### 7. 色の決め方 ［実測して確定］

| 項目 | 内容 |
| --- | --- |
| 対象領域 | ブランドカラーの実装値 |
| 採用パターン | モック `07_brand_direction.jpg` の Direction A を出発点にし、**WCAG コントラスト比を計算してから値を確定**した |
| 採用理由 | モックのパレット（`#F7F4EE` / `#0F1D2D` / `#B23A2E` / グレー）をそのまま使うと、補助グレー `#6B7280` が地に対し **4.40:1** で本文基準の 4.5:1 をわずかに割った。目視では気づけない差なので、計算で `#5D6570`（5.37:1）へ調整した。同様に操作部品の境界線は 3:1 が必要なため `#8F8878`（3.21:1）を採用 |
| 不採用の代替案 | モックの値をそのまま実装する案。→ 見た目は同じでも、読みづらい人が読めないままになる。`W5-9`（アクセシビリティ）で必ず作り直しになる |
| 補足 | 各値のコントラスト比は `globals.css` のコメントに残してある。「近い色に見えるから」で書き換えると基準を割る |

### 8. 比較スロット色は色だけで区別させない ［設計上の制約として記録］

4人比較（`DECISIONS.md` §2）のためスロット色を4つ用意したが、**4色の相互コントラスト比は 1.04〜1.46:1** しかない。
明度がほぼ同じで色相しか違わないため、**色覚特性のある利用者やモノクロ印刷では判別できない**。

→ **色は補助であり、識別子にしない。** 比較画面では必ず A / B / C / D のラベルか選手名を併記する。
`W2-7`（選手比較）と `W2-11`（モバイル）の実装時にこの制約を必ず守ること。

### 9. 外部フォントを取得しない ［暫定］

| 項目 | 内容 |
| --- | --- |
| 採用パターン | Google Fonts 等から**取得しない**。日本語環境に既定で入っている明朝・ゴシックのフォントスタックを指定する |
| 採用理由 | `next/font/google` はビルド時にフォントを取りに行くため、**ビルドがネットワークに依存する**。開発環境では外部アクセスが遮断されており（`08_FEASIBILITY.md` §8.3 と同じ制約）、ビルドが再現しなくなる。ビルドは手元・CI・Vercel のどこでも同じ結果になるべき |
| 不採用の代替案 | ①`next/font/google` で Noto Sans JP を取得 → ビルドがネットワークに依存する。②フォントファイルを同梱して `next/font/local` → ライセンス確認とリポジトリ肥大化。将来必要になれば選択肢 |
| 影響 | 見出しの明朝体は Windows では游明朝、macOS ではヒラギノ明朝になり、**環境によって字面が変わる**。Direction A の「信頼と知性」の方向性は保てるが、モックと完全一致はしない |
| 再検討時期 | `W5-9`（パフォーマンス・アクセシビリティ）。表示速度と見た目の要求を見て判断する |

### 10. クラス名連結を自前で持つ

`clsx` / `classnames` は5行で書ける処理なので、依存を増やさず `src/lib/cx.ts` に自前で置いた
（オーバーライド v3「依存追加前に目的・保守状況・ライセンスを説明する」）。
Tailwind のクラス衝突解決（`tailwind-merge` 相当）はしていない。必要になった時点で導入を検討する。

## 未解決 / オーナー判断が必要

### 依存パッケージの脆弱性（対処済みだが、恒久策は未確定）

`npm install` 直後に `npm audit` で **high 12件** が出ました。内訳と対処:

| 対象 | 内容 | 対処 |
| --- | --- | --- |
| `postcss` (Next.js の依存) | XSS / パストラバーサル等3件 | `overrides` で `^8.5.24` に引き上げ |
| `sharp` (Next.js の画像最適化) | libvips 由来のCVE 4件 | `overrides` で `^0.35.3` に引き上げ |
| `brace-expansion` (ESLint の依存) | DoS | `overrides` で `^5.0.8` に引き上げ |

`package.json` の `overrides` で3つとも解消し、現在 **`npm audit` は 0件** です。

**ただし恒久策ではありません。** `npm audit fix --force` が提示する「正規の修正」は `next@9.3.3` への**ダウングレード**で、これは採用できません。
アドバイザリの影響範囲は `next` の `9.3.4-canary.0 - 16.3.0-preview.7` となっており、**Next.js 15系には修正版が存在しません**。
`overrides` は依存ツリーを強制的に書き換える手段なので、Next.js 側が将来これらの新しいバージョンと非互換になった場合、ビルドが壊れる可能性があります。

→ **Next.js 16系への移行を検討するかどうかは、オーナー判断が必要な項目です。** ROADMAP の「Next.js 15」指定を変えることになるため、無断では実行しません。
